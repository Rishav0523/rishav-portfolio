Why the iteration-cap test matters

The auth suite includes a regression test for the failure that broke admin sign-in: a stored hash above 100,000 iterations made the Workers PBKDF2 call throw instead of returning false, which surfaced as a generic "Something went wrong" message. The implementation now rejects any non-100,000 count before derivation, and the test asserts that it returns false rather than throwing.

Unit tests do not prove the production secret is correct. The stored ADMIN_PASSWORD_HASH value cannot be read back from Cloudflare. If it still encodes 210,000 iterations, sign-in will fail even though every unit test passes. Section 12 records this as an owner action.

Owner actions and conclusions

Actions that require the owner's credentials

  1. Regenerate ADMIN_PASSWORD_HASH at exactly 100,000 iterations if it is still the 210,000-iteration value, then try signing in. Do not pipe a script that might fail into wrangler secret put.
  2. Enable "Always Use HTTPS" in SSL/TLS → Edge Certificates.
  3. Delete the unused Turnstile-shaped secret after confirming nothing depends on it.
  4. Confirm a two-phone AirShare transfer on the same Wi-Fi after the fixes.
  5. Decide whether to enable DNSSEC and whether to add SPF or relax the DMARC record.
  6. Check Web Analytics for visits, or add the beacon snippet if automatic injection is off.

Conclusion

The public site, its API, contact delivery, static asset serving, routing and the browser AirShare flow are working as observed on 31 October 2026. Of 174 automated checks executed, none failed, and both TypeScript configurations passed. The project is not fully verified for production operation until the owner completes the admin-hash action and confirms a two-phone transfer; those two items are the difference between a passing test suite and a fully proven handover.
