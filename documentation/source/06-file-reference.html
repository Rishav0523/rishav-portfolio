How to use this guide

This document is the map from “I want to change something” to “these are the files, in this order.” It describes the repository as handed over at commit 8c9ea09 on 31 October 2026.

  • Paths are relative to the repository root. Commands are for Git Bash from that root.
  • Numbered steps in a recipe are meant to be followed in order.
  • Line numbers are a convenience for this commit; search the named symbol if a line has moved.
  • No recipe requires editing generated output (out/) or touching Cloudflare resources unless it says so.

Two kinds of change

ChangeWhere it is madeDeploy required?Speed
Wording, projects, skills, résumé summary, awardsAdmin dashboard at /admin/, then PublishYes, triggered by PublishOne workflow run
Layout, styling, new page, new endpoint, limitsRepository codeYes, push to mainTypecheck, test, build, deploy
Secrets (admin password, Turnstile, GitHub token)Cloudflare Worker settingsNoTakes effect immediately
Domain, DNS, HTTPS policy, DNSSECCloudflare dashboard and registrarNo code changeMinutes to hours
Database schemamigrations/ + a manual remote applyDeploy code after the applyMinutes
Content is not code. The public pages read a build-time snapshot, content/published.json, which the admin dashboard refreshes through the API during a build. Editing markdown or JSON by hand does not update the live site; use the dashboard.

Reading conventions

  • Paths such as worker/index.ts are click-level targets; a trailing :12 is a line number at this commit.
  • Blue boxes are notes about how the system works; red boxes mark a trap that has already caused a real failure.
  • Figures are numbered by document; “Figure 6.1” is the first diagram in this document.
  • Behaviour labels used in the audit — Working, Partially Working, Requires External Configuration — are defined in document 04.
  • Commands assume Node.js 24 and the Wrangler pinned in the lockfile, run from the repository root.
  • A change is finished when typecheck, tests and build pass locally and the deploy workflow is green.

The content model and its two copies

One JSON document describes everything a visitor reads outside of layout: socials, education, skills, experience, projects, achievements, awards, certifications, résumé summary and profile facts. It exists twice.

CopyLocationWritten byUsed by
LiveD1 site_content.document (row id = 1)Admin Save changesGET /api/content, admin editor
Build snapshotcontent/published.jsonscripts/fetch-content.mjsEvery public page at build time
Do not hand-edit content/published.json and expect the site to change. CI overwrites it from the API on every build. Use the dashboard. A manual edit is only a local fallback for offline builds, and it must be mirrored in the admin or it will disappear.

Modification recipes

Each recipe names the files to open and the follow-up that keeps the docs and tests truthful.

R1 · Change the palette or typography

  1. Open app/globals.css and change the five palette tokens in :root (--cerulean, --teal, --cream, --apricot, --coral).
  2. Adjust the derived surfaces in the same block: --bg, --surface, --card, --ink, --muted, --line, --link, --nav.
  3. If dark mode should shift too, edit the .dark block underneath. Both blocks must stay complete; a missing token falls back to the light value.
  4. Update the theme colour meta tags in app/layout.tsx (light #FDFCDC, dark #04202A) so mobile browser chrome matches.
  5. Regenerate public/images/og.jpg if the social card shows the old palette.
  6. Run npm run build and check one page in both themes at 375 px and 1440 px.

R2 · Add or rename a navigation link

  1. Edit the nav array in lib/site.ts (line 22). Order matters; the header fits eight items at desktop width and collapses below 1280 px.
  2. The href must match an exported route, with no trailing slash in the array (the site adds it in links and the router normalises it).
  3. Add the same route to the routes list in app/sitemap.ts if it is a public page.
  4. Rebuild and check the mobile menu, which renders the same array.

R3 · Add a new public page

  1. Create app/(site)/<slug>/page.tsx. The route group does not appear in the URL.
  2. Export metadata with a title and description; the root template appends the site name.
  3. Read content through lib/content.ts rather than hardcoding strings, or use site from lib/site.ts for global text.
  4. Add the route to app/sitemap.ts and, if it belongs in the header, to site.nav.
  5. Add it to the route lists in tests/e2e.mjs and tests/e2e-responsive.mjs so the new page is covered.
  6. Rebuild and confirm out/<slug>/index.html exists.

R4 · Change wording on the live site

  1. Open https://rishavprasad.in/admin/ and sign in.
  2. Choose the matching tab: Profile, Education, Skills, Experience, Projects, Achievements, Resume.
  3. Edit the fields and choose Save changes. The preview updates; the public site does not.
  4. Choose Publish. A content-published workflow starts; wait for green, then hard-refresh.
When the dashboard has no field for it — a new section, a layout change — it is a code change, not a content change. Follow R1–R3 or add the field to components/admin/content-editors.tsx, the type in lib/content.ts, and the validator in worker/content-schema.ts together.

R5 · Update the résumé PDF

  1. Decide whether the new PDF is approved for publication; do not publish outdated or unapproved details.
  2. With R2 enabled: Admin → Resume → choose the PDF → upload. The Worker stores it under /media/ and sets the link.
  3. Without R2: replace public/resume/rishav-prasad-resume.pdf, keep the same filename, and leave the content link unchanged.
  4. Confirm the résumé page shows the new size and opens the file, and that the print view still fits one page.

R6 · Add a certificate or award

  1. Put the PDF in public/certifications/ using a lowercase hyphenated name.
  2. Admin → Achievements → Certifications → Add certification.
  3. Set href to /certifications/<file>.pdf. Relative paths are checked by the validator; external links must be https.
  4. Save and publish. Open the link from /achievements/ to confirm it resolves.

R7 · Enable R2 media

  1. Enable R2 on the Cloudflare account and create the bucket rishav-portfolio-media.
  2. Uncomment the r2_buckets block in wrangler.jsonc (line 29).
  3. Deploy. /media/missing should now return 404 rather than 503.
  4. Upload one image through Admin → Media and confirm it appears on the site when referenced.

R8 · Rotate the admin password

  1. Run node scripts/hash-password.mjs "<new long password>" on its own and confirm the output starts with pbkdf2_sha256$100000$.
  2. Run npx wrangler secret put ADMIN_PASSWORD_HASH and paste that line at the prompt. Never pipe the script into Wrangler: a refused password stores an empty secret.
  3. Sign in with the new password. To end existing sessions, rotate SESSION_SECRET the same way.
  4. No redeploy is needed; secrets are read at request time.

R9 · Change a rate limit or TTL

  1. Find the constant at the top of worker/index.ts (contact, login, session) or worker/airshare.ts (rooms, signals).
  2. Change the value and the test that asserts it in tests/auth.test.ts, tests/content-schema.test.ts or tests/airshare-protocol.test.ts.
  3. Update documentation/source/02-technical-specification.html and the tables in document 04 so the numbers stay true.
  4. Run npm run typecheck && npm test, then deploy.

R10 · Add an API endpoint

  1. Add the route to worker/index.ts. Public routes go on app; anything touching content, messages or media goes on the admin router, which enforces the session cookie.
  2. Validate input with the helpers in worker/content-schema.ts; never build SQL strings — use .bind().
  3. Return { "error": "…" } with a status code, matching the existing routes.
  4. Add the route to API_DOCUMENTATION.md and a check to tests/e2e.mjs.
  5. If it needs a new binding, add it to worker/env.ts and wrangler.jsonc.

R11 · Change the schema

  1. Add migrations/0003_<name>.sql. Never edit 0001 or 0002; they are already applied.
  2. Apply it locally with npx wrangler d1 migrations apply rishav-portfolio --local.
  3. Apply it to production with --remote before deploying code that needs the new column.
  4. Export a backup first if the migration rewrites data.

R12 · Allow an external script or frame

  1. Add the origin to the script-src or frame-src list in public/_headers.
  2. Keep the existing Cloudflare entries; Turnstile runs in an iframe from challenges.cloudflare.com.
  3. Deploy and retest the contact form and the admin sign-in, which are the two pages that rely on third-party scripts.

Verifying a change

Run these in order before pushing. The first three are also what CI runs, so a green local run predicts a green deploy.

CommandCatchesTime
npm run typecheckType errors in both the app and the WorkerUnder a minute
npm testValidation, auth and protocol regressions (40 checks)Seconds
npm run buildStatic export errors, missing routes, content fetchAbout a minute
npx wrangler dev --port 8787API behaviour with local D1 and .dev.varsManual
E2E_BASE=https://rishavprasad.in node tests/e2e.mjsProduction routes after a deploy (31 checks)Under a minute
Stop the local server before rebuilding. Wrangler reads out/ once at startup; rebuilding under a running server produces stale chunks and ChunkLoadError. Kill the whole Wrangler process tree, not one PID.
